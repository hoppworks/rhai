# Revised bounded process-proof design

Status: design only. No code implementation or fixture execution is authorized by this document. The rejected drafts and stopped attempts remain in Git history and in `correction-attempt.md`; this revision does not erase their findings or reset their cause history.

## Boundary and components

Use the existing `run_scoped.py` only for the Rust build. Fixture execution and its runtime/evidence belong to a project-local supervisor adapter under `.scratch/process-prototype/adapter/` and a run-specific directory under `.scratch/process-prototype/runs/<run-id>/`. Do not change the global runner or agent homes.

The foreground project-local controller is the custodian and sole reaper. It runs outside `run_scoped.py`, remains alive during interruption controls, and owns a direct `Child` handle for each child it starts. The process invoking the controller remains its direct parent and collects the controller's exit status. The controller uses a finite monotonic deadline, a control channel, and nonblocking polling; it does not spawn detached processes. The test subject called the “proof runner” is a project-local adapter child with no child-spawning authority. It receives protocol handles only. The controller starts and owns the proof runner, harness process, workload group leader, same-group anchor, independent pipe-holder, and sentinel. Every successful spawn is installed in a preallocated ownership slot before another spawn, parse, assertion, pipe operation, or other fallible setup. The controller is single-threaded and is the only process allowed to reap these direct children. Harness I/O threads are owned and joined by the harness; if they miss their deadline, the controller terminates and reaps the exact harness process and reports process termination separately from successful cooperative joins.

There is no alarm handler or signal-handler state. A single monotonic event loop checks the control channel, case deadline, and child states with bounded nonblocking operations. The workload leader, anchor, and holder are independently recorded direct children. No fixture creates a grandchild. Any control EOF, runner exit, protocol failure, deadline, or explicit stop enters the same cleanup state machine; control EOF is supplementary to the deadline, not the lifetime guarantee.

## Build and runtime custody

The build command copies the prototype source into `AGENT_RUNTIME_DIR`, sets `CARGO_HOME` and `CARGO_TARGET_DIR` there, and runs under `run_scoped.py --timeout`. Before the scoped command returns, it copies the executable and exact source into a newly created run-specific project directory using temporary files plus atomic rename. It records toolchain, target, and source revision beside them. The later fixture run uses only those project-owned copies, so deletion of Cargo caches and `AGENT_RUNTIME_DIR` cannot remove the executable or source needed for the proof. The binary must have no dependency on the Cargo target/cache paths; inspect its dynamic-library list and record the result before custody starts.

The controller creates and exclusively owns the fixture runtime and evidence directory outside the scoped build runtime. It holds the run directory open/identified by exact path and file identity, rejects symlink substitution, writes bounded run-specific logs and a cleanup receipt, and exports required evidence to the repository evidence directory before removing temporary fixture files. The inner scoped build never owns or deletes the fixture runtime or evidence. The controller removes its own temporary run data only after it has collected every child wait status, confirmed all workers have joined or the harness was killed, published the final receipt, and read that receipt back.

The controller itself is a foreground process, not a detached background service. Its invoking parent owns its process completion/status. Tests do not kill the controller/custodian: they interrupt only its project-local proof-runner child while the controller remains the independent owner. If the controller itself is killed, or the invoking parent and controller are both lost, exact child reaping and readback cannot be claimed; OS reparenting may reap children eventually, but that is outside the proof. A bounded controller deadline limits normal/stalled operation. The design does not claim a hard wall-clock bound in the face of kernel failure, uninterruptible process state, or loss of all supervisors.

## Spawn readiness and safe group identity

Before the workload is spawned, reserve fixed ownership slots, create pipes/control sockets, start the controller's monotonic deadline, and establish the exact evidence destination. Spawn the workload with `CommandExt::process_group(0)` so its PGID is assigned before its code executes; store its `Child` in its ownership slot immediately. The fixture's first line is a complete readiness record containing PID and `getpgrp()`. The controller parses it incrementally and verifies equality before releasing the workload gate. Spawn the anchor into the workload PGID using the spawn attribute, immediately retain its `Child`, and require its complete readiness record to report the same PGID. No work continues until both identities and all other successful spawns have registered with the controller. Expiry at any setup point cleans every registered child; the workload remains gated until this READY handshake succeeds.

The controller is the only sender of signals to the private workload group. For active cancellation it signals `-workload_pid` only while retaining the unreaped direct workload `Child`; it then collects each direct child's actual wait status. It never uses `Child::try_wait` for the workload and never signals a PGID after reaping its leader. The holder and sentinel use their retained exact `Child` handles for termination and reaping.

For normal direct-workload exit, the controller polls `waitid(P_PID, pid, ..., WEXITED | WNOWAIT | WNOHANG)` with zero-initialized `siginfo_t`. `si_pid == 0` means no event yet; other errors fail the case into cleanup. The controller retains the unreaped leader, verifies from the anchor's readiness/owned state that the same-group anchor was established, then signals the group before reaping the leader. It waits for the workload and anchor with its exclusive reaper and records each status. This establishes a concrete test of closure after normal leader exit, distinct from cancelling pipe readers after exit. No `kill(pid, 0)` probe establishes signal identity or group closure. Before fixtures may run, native macOS source/runtime validation must confirm WNOWAIT behavior, group signaling while the leader is an unreaped zombie, and that no `SIGCHLD=SIG_IGN`, `SA_NOCLDWAIT`, competing reaper, `try_wait`, or signal handler can reap the leader. If the native identity invariant fails, stop and preserve logs; never fall back to a stale PID.

## Overlapping I/O and bounded cleanup

The stream fixture reads fixed-size chunks, writes distinct deterministic transforms to stdout and stderr, flushes, then emits a line-complete checkpoint. The harness sends only the first input segment and waits for the full checkpoint before sending the final segment and EOF. The complete payload exceeds pipe capacity. Exact input transfer, expected output counts/checksums, and successful exit are asserted. The checkpoint ordering proves input/output overlap without timing assumptions.

All controller reads/writes and child polling are nonblocking and bounded per event-loop pass. Workers use nonblocking FDs, capped poll timeouts, bounded buffers and work per wakeup, EINTR/EAGAIN handling, and stop checks between operations. They do not wait for inherited-pipe EOF after cancellation, use unbounded locks, block while flushing buffered output, or close a descriptor owned by another worker. The harness owns every worker handle. It checks `is_finished` before joining; if workers do not finish before the case deadline, the controller terminates/reaps the exact harness process. Such a case records worker completion as unverified/failed, even though process termination prevents those threads from surviving. No unbounded `wait`, `join`, or `read_to_end` is allowed.

## Interruption and negative controls

The controller implements a finite per-case deadline and a separate outer deadline. When a case deadline expires, it requests cooperative stop from the proof runner/harness, polls until the grace deadline, then signals the exact unreaped harness or proof-runner child, escalating to `SIGKILL` only while its `Child` handle is retained. It independently closes the workload group while its leader remains unreaped, terminates the independent holder and sentinel by exact child handles, polls/reaps every direct child, and reads back the receipt. Cleanup continues after each error; a failed operation does not skip the remaining owned resources. If any OS termination or wait cannot complete before the controller deadline, record incomplete cleanup, preserve the run directory and evidence, return failure, and make no clean-run claim.

Run separate controls for:

1. a live-resource assertion failure after readiness and while I/O workers are active; require the intended assertion diagnostic, exact wait statuses for workload/anchor/holder, actual worker joins, and sentinel survival until its own exact cleanup;
2. a controlled timeout of the project-local proof runner while workload, anchor, holder, sentinel and harness workers are live; leave the controller alive, verify bounded fallback, exact cleanup/readback, and distinguish joined workers from harness termination;
3. abrupt `SIGKILL` of the project-local proof runner while the same resources are live; the controller remains alive and proves runner reaping, fixture cleanup and sentinel preservation;
4. normal direct-workload exit followed by managed group closure and post-exit I/O cancellation while the independent holder retains output pipes;
5. a separate actual `run_scoped.py --timeout` control with no private groups, verifying status 124 and reliable wrapper status propagation. This control does not count as private-group cleanup proof.

The scoped invocation redirects command output to a run log, captures status immediately, then exports the log. Passing-case nonzero status fails. Every negative control must show its intended diagnostic and cleanup records, not merely a nonzero exit. The outer controller is always alive for the active-private-resource interruption controls and reaps its owned children. It is not itself killed in these tests.

## Required pre-run review and remaining boundary

Before implementation can run fixtures, review must verify: immediate child registration; complete READY gating; no hidden/escaped children; exclusive wait ownership; `WNOWAIT | WNOHANG` no-event/error handling; group identity retained until the last signal; bounded polling and escalation; harness thread ownership; runtime/evidence separation from `AGENT_RUNTIME_DIR`; controller parent/child lifecycle; and exact readback before deletion. A missing property means no fixture run.

**Open requirement boundary:** does acceptance require private-fixture cleanup when the actual shared `run_scoped.py` process itself is SIGKILLed while fixtures are live, or is interruption of the reviewed project-local runner adapter plus an actual no-private-group `run_scoped.py` timeout control sufficient? The unchanged shared runner creates a separate internal supervisor session and deletes its private runtime on timeout; a local controller cannot safely own/reap those hidden internal children without changing/copying that runner. This design does not claim cleanup of live private fixtures under abrupt death of the shared runner. Affected requirement: whole-runner timeout/SIGKILL cleanup. Resume implementation only after the owner accepts the adapter boundary or authorizes a project-local scoped-runner copy with explicit supervisor PID/ownership and runtime-custody behavior. No fixture execution should begin while this decision is open.

Claims remain native macOS only. Rust 1.77.2 compilation, Linux/Windows behavior, escaped-descendant ancestry, production Rhai API, output limits/deadline policy, and the release matrix remain open. Historical evidence files are retained unchanged and remain historical observations.
