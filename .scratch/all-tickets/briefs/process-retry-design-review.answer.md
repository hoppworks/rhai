# Process retry supervision design review

## Decision

**Reject `retry-design.md` at `2a3996cdaaed36ce2e4de6a292d1764af0bed700` as authorization to execute fixtures.** The unreaped-leader approach is supportable, but the complete ownership and interruption design is not safe yet. The explicit exclusion of orchestrator/scoped-runner disappearance contradicts the accepted correction requirement. A harness-death test cannot substitute for whole-runner interruption.

This was a read-only review. No build, fixture, signal experiment, guest operation, source correction or remote write was performed. The prototype worktree was clean at the specified commit. The original rejected proof and the stopped first correction remain rejected; this review neither resets their history nor consumes an implementation attempt by running anything.

## Exact blockers

| Area | Defect and consequence | Required correction |
| --- | --- | --- |
| Runner interruption | `run_scoped.py` kills only its own supervisor group. Guardian, workload and holder use other groups. Its `finally` then removes the runtime without waiting for their cleanup. A shorter guardian lease does not impose ordering when interruption happens early. | A surviving owner must supervise every private scope and retain the runtime until cleanup/readback completes. |
| Runner death | SIGKILL bypasses the runner's `finally`; the `_supervise` helper has no independent timeout. If the orchestrator is gone, the proposed guardian owns neither that helper nor the sentinel, and nobody specified can collect all direct-child statuses. | Put interruption supervision and runtime custody outside the runner being interrupted; make exact parentage and reaping responsibility explicit. |
| Partial setup | “First operation” alarm arming and a harness start gate do not define every transition between child creation, handle installation, PID publication and expiry. The handler only kills the workload group; a holder or other successful spawn can exist while no workload PGID is published. | No fixture gate opens before the independent owner is ready. Every successful spawn is registered before another fallible operation; expiry/setup failure takes one cleanup path for every registered child. |
| Exit observation | `waitid(P_PID, ..., WEXITED \| WNOWAIT)` lacks `WNOHANG`. It can block indefinitely while the child runs. The stated general `waitpid(..., WNOHANG)` loop must never reap the workload leader before the last group signal. | Use `WEXITED \| WNOWAIT \| WNOHANG`, zero-initialized `siginfo`, explicit no-event handling and a single exclusive reaper. |
| Signal protocol | Type, memory access, inherited mask/disposition, other threads, pending alarms and errno handling are unspecified. Blocking SIGALRM across potentially blocking spawn/wait disables the independent lease. | Use the concrete protocol below, or remove signal-handler state from the cleanup mechanism in favor of a surviving polling custodian. |
| Worker shutdown | Rust has no deadline argument to `join`. Stop tokens and nonblocking descriptors alone do not prove that arbitrary worker code, error paths and destructors finish. The orchestrator cannot join threads belonging to the harness process. | The harness owns and joins its threads. A separate owner bounds the harness process lifetime and records process termination as the failure fallback, without claiming cooperative joins occurred. |
| Readback | A receipt inside a deleted runtime is unavailable. A guardian receipt alone cannot prove the orchestrator reaped the guardian, nor can a disappearance probe prove exact-child reaping. | Export durable, run-specific evidence outside the runner's deletion domain; use the actual parent's wait status for each child and a surviving observer for the interruption control. |

These are launch gates, not optional documentation improvements.

## PID and group lifetime

The intended normal-exit sequence is sound in principle: keep the workload as an unreaped direct child; observe its exit without reaping; close its group; only then clear the published identity and reap. Apple's XNU `waitid` implementation skips `reap_child_locked` when `WNOWAIT` is present. The installed macOS SDK also exposes `WNOWAIT` and `WNOHANG`. This establishes a source basis for non-reaping observation, not native behavioral acceptance. [Apple XNU exit/wait implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_exit.c)

The identity argument requires all of the following: normal zombie retention; no `SIGCHLD=SIG_IGN` or `SA_NOCLDWAIT`; no competing `wait`, `try_wait`, generic child-reaper thread or signal handler; workload group establishment before its code runs; and no fixture `setsid`/`setpgid` escape. Verify the retained zombie PID and group allocation behavior against the runner's actual macOS/XNU version before accepting the native result. Apple's kernel maintains PID and process-group tables separately, so “the zombie pins a PID” must not be presented as an untested assertion that the process group still contains a live target. [Apple XNU process implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_proc.c)

The anchor supplies a real remaining target and must have a complete readiness record showing the expected PGID. Gate workload exit until the anchor is registered and ready. Keep the anchor's handle unreaped too. An anchor that exits unexpectedly makes the intended scope-closure case fail; it does not permit using a stale PID. No kill-zero check is needed to establish signal identity. Negative `kill` targets a group, and its success is not evidence that each expected fixture member exited; collect each direct-child wait status separately. [Apple kill manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/kill.2.html)

## Minimum supportable amendment

There is **no safe alarm-only amendment inside the existing orchestrator topology** that supplies whole-runner interruption and readback. The smallest structural amendment is to promote the guardian into a runner-level custodian and remove redundant fixture owners. This requires a reviewed runner adapter/runtime-ownership change; the unchanged `run_scoped.py` cannot provide it. Do not silently modify the global runner or treat this answer as permission for such a modification.

1. **Establish custody before any proof fixture.** A surviving control process starts and retains the custodian's exact child handle. The custodian lives outside the scoped runner's termination group, starts no fixture until its finite monotonic deadline, control channel, runtime custody and evidence destination are installed, and acknowledges READY. Failure before READY can create no proof fixture; the control process terminates/reaps the exact custodian if startup fails. The control process remains alive during runner-interruption tests and later reaps the custodian.

2. **Give the custodian direct ownership of proof resources.** It spawns the orchestrator, harness, workload leader, anchor, independent holder and sentinel itself, retaining every successful spawn before parsing, pipe setup or another spawn. The harness receives descriptors and protocol access, not ownership of a child it cannot reap. Custodian receipt entries distinguish each exact child and its real wait status. This merges the proposed guardian with the independent lifetime owner rather than adding a second unproven lease chain. The harness owns its I/O threads; no other fixture spawns descendants. Group formation remains atomic with child launch, and the anchor is in the custodian's session so it can join the workload group.

3. **Retain scope and runtime ownership through interruption.** The custodian reacts to monotonic expiry, control EOF, runner exit, protocol failure or an explicit stop request by closing every still-owned scope and reaping its direct children. EOF detection is supplementary to the finite lease: use close-on-exec descriptors and close unrelated copies so descendants cannot keep control EOF suppressed. A reviewed adapter must prevent the inner runner from deleting the fixture/evidence runtime before the custodian completes; alternatively the custodian owns a distinct fixture runtime that the inner runner never deletes, with explicit project configuration and exact cleanup responsibility. The runner's private build runtime can keep its existing cleanup behavior only if no active fixture or pending fixture receipt depends on it. Receipt export precedes removal of the custodian-owned runtime.

4. **Bound the controller, not just the requested work.** Keep the custodian single-threaded, with nonblocking control I/O, bounded per-iteration work and non-reaping workload observation. It does not join harness threads. It first requests cooperative stop; if the harness fails to exit by its grace deadline, it kills the exact unreaped harness child and collects its status. For other exact children, request termination and escalate to SIGKILL while identity is still retained. Poll waits rather than performing an unconditional wait. If the OS cannot complete termination/reaping, record incomplete cleanup, retain the exact ownership/runtime data and fail; never delete evidence or claim cleanup succeeded. An OS scheduling/kernel failure or loss of every independent supervisor cannot be given an absolute wall-clock guarantee.

5. **Prove runner interruption explicitly.** In separate controls, interrupt the orchestrator and the scoped runner with live workload, anchor, holder and harness workers. Cover caught termination/timeout and abrupt runner death. The surviving control process reads the custodian receipt, verifies the intended interruption status, matches child-authored readiness/identity records and collected parent wait statuses, and reaps the custodian. Verify sentinel survival before its own exact cleanup in cases where that survival is expected. Record cooperative worker joins separately from harness-process termination. A no-private-group wrapper timeout control remains useful but does not close this gate.

This topology is a supportable design direction, **not approval of an implementation that has not been written or reviewed**. If a bounded local adapter cannot establish these relationships within the owner's authorized scope, stop and consult the owner. Do not weaken the runner-interruption requirement or open another escalation for this cause.

## If the alarm handler is retained

The simpler amended custodian can enforce its lease by bounded polling; its event loop must not perform a blocking join/read/wait. Retaining the proposed alarm as an additional backstop requires all these details:

- Install and check `sigaction` before `alarm`, explicitly unblock SIGALRM, reset inherited SIGCHLD behavior to preserve waitable children, and reject unexpected dispositions. Remain single-threaded. If threading is introduced, signal masks are per thread and every delivery path must be specified.
- Use a tiny audited C boundary with `volatile sig_atomic_t` state and a checked representable positive PID, or separately establish the exact Rust atomic/FFI safety argument. No allocation, formatting, locks, Rust unwinding or ordinary shared Rust mutable state in the handler. Save/restore errno. Set expiry first; preserve syscall failure diagnostics using signal-safe state. `kill` is listed as async-signal-safe, but that does not make surrounding Rust operations safe. [Apple sigaction manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/sigaction.2.html)
- Block SIGALRM only for short nonblocking publish/clear transitions. Publish only after the unreaped child is registered. On cleanup, perform the last group signal before clearing the PGID; clear before reaping; keep SIGALRM blocked across clear/disarm and safely handle any pending alarm before restoring the mask. Every loop/spawn transition rechecks expiry so an alarm with no published PID cannot be followed by a fresh workload launch.
- Do not hold the mask across spawn, wait, output export or other potentially blocking operations. A child created during an interrupted spawn must remain gated and take the registered-child cleanup path before it can execute work. Children inherit signal masks across exec, so explicitly restore the intended fixture mask in the supported launch boundary. [Apple signal-mask manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/sigprocmask.2.html)
- An alarm is delivered by scheduling the process and does not rescue a stopped, killed or permanently blocked guardian. It is not an independent OS process-tree ownership facility. Its timer fires once and must not be accidentally replaced by another alarm. [Apple alarm manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/alarm.3.html)

## Concrete worker bound and evidence limits

Each worker owns its nonblocking descriptor, checks a stop token between bounded reads/writes, uses a finite poll timeout capped by the case deadline, handles EINTR/EAGAIN, and treats EPIPE/SIGPIPE without killing the supervisor. Protocol buffers and work per wakeup are bounded. No worker waits for inherited-pipe EOF after cancellation, takes an unbounded lock, flushes a blocking buffered writer, or closes a descriptor owned by another active thread. Check `is_finished` before consuming a join handle, allowing the harness to stop waiting and let its parent terminate it on failure. Rust documents that `join` waits for thread termination including destructors; `is_finished` enables a nonblocking join pattern but is not a universal hard-time guarantee. [Rust JoinHandle documentation](https://doc.rust-lang.org/std/thread/struct.JoinHandle.html)

The accepted passing cancellation case must show actual worker completion and joins despite the live holder. An externally killed harness proves its workers cannot continue after process termination; it does not prove successful cooperative cancellation or joins. Partial thread-start failures retain every already-created handle and use the same stop/fallback path.

The receipt must identify the run, roles, registered children, termination results, collected statuses, incomplete operations and runtime path. Use a pre-established evidence directory outside the inner runner's cleanup domain, bounded records and atomic publication; filesystem durability failure is an evidence failure, not a passing cleanup receipt. Independent readback must happen before final deletion. Killing all supervisors, machine failure, or kernel/filesystem failure remains an explicit exceptional limitation with retained recovery data, not an accepted proof scenario.

The stream overlap gate and explicit exit-status capture in the draft remain useful. Nothing here accepts Rust 1.77.2 compatibility, Linux/Windows behavior, escaped-descendant ancestry, production Rhai API behavior, output limits/deadline policy or the release matrix. Historical observations remain historical observations.
