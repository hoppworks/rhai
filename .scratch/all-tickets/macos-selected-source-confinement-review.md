## Process behavior found

The workspace build script [`build.rs`](../../build.rs) reads hashing-seed environment variables and writes the generated hashing configuration (lines 7–28); it has no process-spawn path. [`codegen/src/lib.rs`](../../codegen/src/lib.rs) implements proc-macro entrypoints using `proc_macro`, `syn`, and `quote` (notably lines 35, 75, 115, 161, 179, 220); its reviewed source does not spawn processes, resolve helper executables, or change process groups/sessions. The same direct-source result applies to all 34 candidate registry proc-macro modules: `const-random-macro`, `paste`, and `serde_derive`. Their work is token parsing/generation inside rustc's proc-macro execution.

Several build scripts do spawn compiler probes. Their child selection is significant: absent a wrapper they use Cargo's `RUSTC`; where present they honor `RUSTC_WRAPPER` (and, in some helper crates, `RUSTC_WORKSPACE_WRAPPER`). `cap-primitives` runs five feature probes from `main` regardless of target (`build.rs` lines 4–10, 41–90); `cap-std` runs three (`build.rs` lines 4–10, 37–86); and `io-extras` runs its feature probes from `main` (`build.rs` lines 4–13, 33–82). The helpers pass `TARGET` and, when set, `CARGO_ENCODED_RUSTFLAGS`, spawn rustc, pipe stdin and wait synchronously. They have no timeout or explicit process-tree/job control. `rustix` always performs the lower/upper `NonZero` and diagnostic probes (lines 78–90, 200–213, 231–275); on the selected macOS target its source selects the libc backend and the `apple` cfg (lines 132–158). It also takes target/feature-dependent branches, including no-std and experimental-feature probes; whether those extra branches run depends on actual unit features and injected cfgs.

`proc-macro2`'s build script queries the compiler version and performs compile probes (`build.rs` lines 14–15, 165–256; version helper at 248–256). `quote`, `paste`, `serde`, and `serde_core` run rustc version queries (`build.rs` lines 5–8 and 24–33; 5 and 28–37; 19–29 and 60–69; 18–29 and 104–119 respectively); `zerocopy` queries its compiler at lines 232–264. These invoke the selected `RUSTC`; `proc-macro2` additionally honors wrapper variables and compile flags. The exact source paths and line matches for these files are recorded in the accepted inventory, and the direct command construction has no `setsid`, `setpgid`, `fork`, or equivalent session/group-detach call.

There are also indirect compiler helpers that a scan of only each candidate `build.rs` would miss. `ahash/build.rs` calls `version_check::supports_feature` (lines 7–9); locked `version_check-0.9.5/src/lib.rs:155–161` resolves `RUSTC` from its default or environment and executes `rustc --verbose --version`. `num-traits/build.rs:1–6` uses `autocfg::new`; `smartstring/build.rs:5–17` uses both `autocfg` and `version_check`. Locked `autocfg-1.5.1/src/rustc.rs:28–64` selects `RUSTC` and recognizes Cargo wrapper variables, while `src/lib.rs:306–330` spawns compiler feature probes and waits for them. These children inherit Cargo-provided compiler/wrapper configuration; they do not provide independent process-tree containment.

Platform gates reduce, but do not erase, the candidate list. `getrandom-0.3.4/build.rs:42–56` calls its compiler-version helper only for `CARGO_CFG_TARGET_FAMILY == "windows"` (helper at lines 7–31), so that source path is not taken for macOS. `io-lifetimes` 2.0.4 and 3.0.1 call their probe only when `CARGO_CFG_TARGET_OS == "wasi"` (`build.rs:4–15`), so their probe is likewise inactive on macOS. In contrast, `libc-0.2.189/build.rs:87` always calls the rustc-version query (helper lines 240–269). It also calls `emcc_version_code` from `main` (lines 137–141); on non-Windows it constructs the bare executable name `emcc` and runs `emcc -dumpversion` (lines 337–345), tolerating failure. This is PATH-based helper resolution on macOS, so exact `PATH` and any resolved executable remain an assumption. Its `freebsd-version` helper (lines 117–124, 318–335) is conditional on `LIBC_CI` and the FreeBSD override; it does not run under the ordinary non-CI/no-override branch. VxWorks behavior is environment/cfg gated. `portable-atomic` always queries compiler version through `version.rs:5–20`, using `RUSTC` and optional `RUSTC_WRAPPER`; it does not apply `RUSTC_WORKSPACE_WRAPPER` (`version.rs:8–15`). Its remaining build branches use target/compiler environment. The other candidate build scripts generate files or cfg output without a direct process API. The source inventory's empty lexical process matches were treated only as pointers for inspection, not as proof by themselves.

## Confinement conclusion and limits

Within these reviewed candidate sources, I found no explicit source path that creates a new process group/session or detaches a child. The compiler helpers synchronously wait on their immediate children. That does not prove descendant custody: a wrapper, compiler, or helper may itself launch descendants or detach; Cargo's ordinary child waiting is not by itself a process-tree cleanup guarantee. The accepted Cargo source review separately found the `setsid()` path only under its test-only opt-in environment variable, which the recorded harness allowlist omits. That narrows a known Cargo source path but does not validate native group/session behavior or descendants at runtime.

For source coverage, the conservative metadata superset is adequate to review these candidate build/proc-macro sources for the recorded lock, workspace members, target and feature union. It does not establish that this is the exact unit graph the selected measurement command will execute: metadata does not identify every host/target unit activation or dynamic helper path. This review therefore closes only the source candidate review prerequisite. It makes no native launch, measurement, cleanup, process-tree, or acceptance claim.

Remaining exact/runtime assumptions include the selected executable for `RUSTC` and any allowed wrappers, Cargo configuration that could affect compiler selection/flags, `PATH` resolution for libc's `emcc` probe, and the actual macOS SDK / `xcrun` / linker / `dsymutil` tools reached by rustc in a real build. This source-only work did not run or query those tools, build scripts, proc macros, or native process controls. The prior source audit's toolchain-source and Darwin native-reader items remain unverified and are not changed here.
