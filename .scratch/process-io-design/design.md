# Private Rust process I/O boundary

Status: private design; production code remains pending. Native standalone Rust parent I/O is now accepted on macOS and Linux with exact Rust1.77.2: see `.scratch/all-tickets/native-linux-io-proof-review.md` and the current coordinator state. Historical prerequisite descriptions below record the evidence available when this design was written; they do not invalidate the later accepted proof. Workload-spawned descendant topology, production Engine semantics and Windows remain open.

## Decision

Keep process ownership in one private `ProcessOwner` state machine and isolate OS-specific pipe operations behind a small private adapter. Do not implement the production stream pump as threads blocked in `std::io::Read` or `Write`. The accepted contract requires cancellation to finish even when an escaped or unmanaged process retains a pipe handle. Killing and reaping the direct child cannot make such a pipe reach EOF, so joining blocking workers is not a cancellation mechanism.

The adapter should expose owned, cancellable reader and writer endpoints plus `poll(deadline)`, `cancel_all()`, and `join_and_close()`. It reports for each stream whether it reached EOF, was canceled, or failed. `cancel_all` requests kernel cancellation and wakes any readiness wait; `join_and_close` waits for operation completion before releasing endpoint state. The owner retains the child/job/group handles, all endpoints, worker state, bounded buffers, and cleanup result until the direct child is reaped, the managed scope is closed if selected, and every I/O worker has stopped. If cleanup fails, retain the owner and surface incomplete cleanup; do not publish successful cleanup or discard the only OS handles.

Use one bounded input queue, with a configured maximum chunk in flight, and bounded output retention per stream. Readers drain stdout and stderr while the writer advances stdin. Permit exactly N bytes for a stream with cap N. Retain no more than that prefix and raise `OutputLimit` only after observing byte N+1; a zero cap therefore fails on the first byte. Preserve the ticket’s supervisor cause rule: if deadline and overflow are both observed in the same supervision step, `OutputLimit` wins; otherwise keep the first committed cause, with cleanup failures recorded only as secondary diagnostics. The supervisor stops accepting input, requests child/scope termination, cancels outstanding pipe operations, collects operation completions, and reaps. This bounds both retained output and queued input independently of child speed.

## Platform adapters

On Linux and macOS, set the owned parent pipe descriptors nonblocking and drive read/write readiness with `poll` or the platform equivalent. Register a private wake pipe alongside those descriptors. Cancellation writes the wake pipe, releasing the poll loop even if a child or descendant keeps stdout/stderr open or stdin is backpressured. On wake, stop issuing I/O, close the owned parent ends, and join the adapter worker. Retry interrupted syscalls and treat `EAGAIN` as a readiness transition. Do not use fixed sleeps. The accepted Darwin package did not demonstrate Rust I/O workers: its Python scoped runner/custodian used `select`, Python threads, `os.read` and `os.write`; the Rust executable was invoked only for `--fixture stream`, `--fixture stall`, and `--fixture anchor`. This design's explicit wake descriptor and Rust cancellation remain unproven.

On Windows, use parent-side named-pipe handles opened for overlapped I/O, with child-side handles connected to standard input/output/error. Keep each pending `OVERLAPPED` structure and its event alive until `GetOverlappedResult` observes completion after `CancelIoEx`. Cancellation is a request, not completion; never free or reuse the structure or close its event merely because `CancelIoEx` returned. The worker waits on I/O completion and an owner cancellation event, then drains the completion before joining. A synchronous `ReadFile`/`WriteFile` worker plus `CancelSynchronousIo` is weaker: Windows documents cancellation as an attempt and warns about races when the target thread starts another I/O. Prefer one outstanding operation per endpoint with explicit overlapped state. For managed scope, a private launcher must ensure the process enters its owned job before user code can execute (for example, create suspended, assign to the job, then resume); fail closed on assignment failure. Validate named-pipe handle inheritance, stdio wiring, suspended launch, and job behavior on native Windows before fixing construction details.

Direct-child termination uses the owned `std::process::Child` handle and `Child::kill`/`wait` where the standard launcher is used. Managed mode remains distinct. Unix can request a new process group as part of spawn (`CommandExt::process_group(0)`); signal the owned group through a reviewed native binding. Group membership does not cover descendants that deliberately escape. In managed Unix mode, do not use `Child::try_wait` to detect leader exit because it reaps the leader and can release its PID/PGID identity. Observe exit without reaping (for example, reviewed `waitid` with `WNOWAIT`), keep the leader unreaped as the pinned group identity through the final group signal, then reap it with `wait`; native proof must establish this ordering on Linux and macOS. Never signal a stale numeric PGID after the identity owner is gone. Windows managed scope uses `CreateProcessW(CREATE_SUSPENDED)`, retains both `PROCESS_INFORMATION` handles, assigns the process to the owned job, then calls `ResumeThread` through the retained primary-thread handle. The private Windows owner retains and uses the native process handle for query/wait/direct-child termination and the job handle for managed termination; it does not attempt to manufacture a stable `std::process::Child` from raw `CreateProcessW` state, rediscover a PID/thread, or rely on nightly-only `ChildExt::main_thread_handle`. Keep both process and thread handles owned through setup/rollback and release the thread handle only after resume or confirmed setup cleanup. Native setup must establish membership before user code can run and fail closed if assignment cannot be guaranteed. Job association can be constrained by the host’s existing job hierarchy and breakaway policy. The accepted setup-race, existing-job, and partial-failure tests remain required. Neither process groups nor jobs are a security sandbox.

`Child::try_wait` is suitable for direct-child mode, but not for discovering managed Unix leader exit while the PGID must remain pinned. In every mode, pipe completion is tracked separately: a direct child may exit while a descendant still holds a pipe. Spawn itself may not be interruptible, so the run deadline starts immediately before spawn and that limit must be documented. The owner must not hold a mutex while blocking in I/O or child wait; cancellation must remain available concurrently.

## Dependency assessment

The core feature remains at Rust 1.66 and receives no OS dependency. The optional `sys`/`net` surface has an approved Rust 1.77.2 floor. If implemented with direct system calls, use explicit optional target dependencies behind `sys`, not transitive crates:

* `libc` for POSIX descriptor flags, readiness polling, wake pipe, and process-group signals. The official current 0.2 README states Rust 1.65 minimum. That is below the optional floor. The existing `Cargo.msrv.lock` already resolves libc transitively, but that does not authorize a direct dependency.
* `windows-sys` for Windows pipe, event, overlapped-I/O, cancellation, and job-object declarations. The current 0.61.2 manifest declares Rust 1.71 and edition 2021, below the optional Rust 1.77.2 floor. The minimal feature set for the described raw APIs is `Win32_Foundation`, `Win32_Security`, `Win32_Storage_FileSystem`, `Win32_System_IO`, `Win32_System_Pipes`, `Win32_System_Threading`, and `Win32_System_JobObjects`. `ReadFile`/`WriteFile` are in `Storage::FileSystem`; named-pipe construction is in `System::Pipes`; overlapped completion/cancellation are in `System::IO`; event/process creation and resume are in `System::Threading`; and job operations are in `System::JobObjects`. `SECURITY_ATTRIBUTES`, used by pipe, event, job, and process creation signatures, is under `Win32::Security`. The feature declarations cascade through their parent namespaces, including `Win32_Foundation`. Therefore the concrete design candidate is optional target dependency `windows-sys = 0.61.2` with only the listed features. Upstream windows-rs guidance recommends the `>=0.59, <=0.61` version range for resolver flexibility and fewer duplicate versions; this is guidance, not a maintenance/support guarantee. The lockfile's existing transitive 0.59.0 is not a reason by itself to select the older line.

Keep both dependencies optional and linked only through `sys` (and only on their applicable targets), leaving the core feature graph dependency-free at Rust 1.66. This is the design choice, not proof: Cargo resolution/feature-tree inspection at optional Rust 1.77.2 and core-only Rust 1.66 builds remain pending. Current local resolution includes libc 0.2.171 and windows-sys 0.48.0, 0.52.0, and 0.59.0 transitively; selecting 0.61.2 may temporarily add another version until dependency families align. The older lock entries do not establish direct dependency suitability. Avoid adopting Tokio/Mio merely to obtain readiness: the contract needs explicit cancellation and ownership, and their MSRV/features require the same review.

## Evidence boundary

The accepted package used Python controller/custodian scripts and Rust stream/stall/anchor child fixtures. On native Darwin 27 arm64 with Rust/Cargo 1.93, the custodian invoked the Rust executable only as `--fixture stream`, `--fixture stall`, and `--fixture anchor`; the historical bare Rust entry point was explicitly not run. In `adapter/run_scoped.py`, Python threads perform parent-side I/O using `select`, `os.read`, and `os.write`. Receipts establish controller/custodian interruption behavior, exact child cleanup, and scoped runtime removal for those modes, not Rust I/O-worker cancellation. References: `.scratch/process-prototype/README.md`, `.scratch/process-prototype/adapter/run_scoped.py`, `.scratch/process-prototype/coordinator-state.md`, and `.scratch/all-tickets/process-source-gate-review.md`.

No accepted evidence proves Rust reader/writer cancellation. The design's poll-plus-wake adapter, bounded production capture, deadline/output-limit precedence, spawn/setup rollback, Linux/macOS native Rust behavior, Windows behavior, Rust 1.77.2, and production Rhai `Engine` semantics remain unproven. No full cancellation gate is accepted.

## Next failing native acceptance test

Add a standalone Rust adapter acceptance test on native Linux before integrating with Rhai, using the accepted scoped-runner/custodian pattern for interruption-safe ownership. The child fixture starts an independently identified descendant that inherits stdout and stderr, publishes readiness, and keeps the pipes open. The parent begins a large stdin write while concurrently draining both output streams. Before cancellation, require an explicit worker handshake proving both readers and the writer have entered the adapter and are active or blocked on readiness/backpressure; child readiness alone is insufficient. Then request cancellation without closing the descendant. Include a missing-wake control, but keep it self-cleaning: bound the observation interval, assert workers did not join from the broken cancel request, then invoke a separately retained emergency wake before teardown so the expected failing assertion cannot strand workers. The outer custodian must retain exact process/group identity and clean every descendant on interruption. In the correct path assert the wake releases each pending reader and the blocked/backpressured writer, all workers join, output stays within configured caps (N accepted, N+1 fails), EOF is incomplete, the managed group identity stays pinned through its final signal, the direct child is reaped, any deliberately escaped descendant is independently reaped, and an unrelated sentinel remains alive. This targets the selected nonblocking-plus-wake design, which the accepted Darwin Rust prototype did not exercise.

Then run an equivalent native macOS wake-descriptor test. The accepted Darwin package used Python I/O workers, so it contributes no Rust I/O-worker proof. Native Windows proof must separately exercise overlapped cancellation and completion-state lifetime. Rust 1.77.2 and production Engine integration remain later gates.
## Official platform references

* Rust [`Child`](https://doc.rust-lang.org/std/process/struct.Child.html): dropping a child does not terminate or reap it; `try_wait` is nonblocking and repeated completed waits preserve status.
* Rust Unix [`CommandExt::process_group`](https://doc.rust-lang.org/std/os/unix/process/trait.CommandExt.html).
* Microsoft [`CancelIoEx`](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex): cancels pending overlapped requests, but completion must be observed before `OVERLAPPED` storage is reused or released.
* Microsoft [canceling pending I/O](https://learn.microsoft.com/en-us/windows/desktop/FileIO/canceling-pending-i-o-operations): documents synchronous cancellation attempts and thread-I/O races.
* Microsoft [job objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) and [`AssignProcessToJobObject`](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject): describe job association, child membership, and host job constraints.
* Official [`libc` README](https://docs.rs/crate/libc/latest/source/README.md): current stated MSRV is Rust 1.65; recheck the exact selected release during implementation.
* Official [`windows-sys` 0.61.2 manifest](https://docs.rs/crate/windows-sys/0.61.2/source/Cargo.toml.orig) and [0.61.2 API docs](https://docs.rs/windows-sys/0.61.2/windows_sys/): confirm the Rust 1.71 floor and Windows API feature declarations; official [windows-rs guidance](https://docs.rs/crate/windows-sys/latest/source/readme.md) recommends versions through 0.61 to avoid duplicate versions.
* Official [`ReadFile`](https://docs.rs/windows-sys/0.61.2/windows_sys/Win32/Storage/FileSystem/fn.ReadFile.html) and [`WriteFile`](https://docs.rs/windows-sys/0.61.2/windows_sys/Win32/Storage/FileSystem/fn.WriteFile.html), [`CancelIoEx`](https://docs.rs/windows-sys/0.61.2/windows_sys/Win32/System/IO/fn.CancelIoEx.html), [`CreateNamedPipeW`](https://docs.rs/windows-sys/0.61.2/windows_sys/Win32/System/Pipes/fn.CreateNamedPipeW.html), [`CreateProcessW`](https://docs.rs/windows-sys/0.61.2/windows_sys/Win32/System/Threading/fn.CreateProcessW.html), [`SECURITY_ATTRIBUTES`](https://docs.rs/windows-sys/0.61.2/windows_sys/Win32/Security/struct.SECURITY_ATTRIBUTES.html), and [`CreateJobObjectW`](https://docs.rs/windows-sys/0.61.2/windows_sys/Win32/System/JobObjects/fn.CreateJobObjectW.html) signatures establish the API namespaces and security-attribute type dependency.
* Microsoft [`CreateProcessW`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw): documents `CREATE_SUSPENDED` for setup before user code runs.
* Microsoft [`ResumeThread`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread), [`TerminateProcess`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess), and [`GetExitCodeProcess`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getexitcodeprocess): document use of retained thread/process handles for launch continuation, direct-child termination, and status observation.
